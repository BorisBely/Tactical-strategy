

# Часть 1. Итоговая модель состояний

Я предлагаю окончательно принять:

```text
NotReady
    ↓ Ctrl+E / боевой переход
LowReady
    ↓
HighReady
    ↓
Aiming

LowReady → HipFire
LowReady → PointAim

HighReady → Aiming
HighReady → PointAim
HighReady → HipFire
```

То есть:

### 1. NotReady

Мирное, расслабленное состояние.

```text
Animator:
    Stand_Relaxed_Idle

WeaponReady:
    false

AimProgress:
    0 / не накапливается

Fire:
    запрещён
```

Смысл:

> «Контакта сейчас не ожидаю».

---

### 2. LowReady

Первый уровень боевой готовности.

```text
Animator:
    Stand_Aim_Idle

WeaponReady:
    true визуально
    но Fire = false

AimProgress:
    не накапливается
```

Смысл:

> «Я уже в боевой стойке и готов быстро поднять оружие, но пока не держу его на конкретной цели».

---

### 3. HighReady

Непосредственно перед Aiming.

```text
Animator:
    Stand_Aim_Idle

Weapon:
    уже направлено в сторону потенциальной угрозы

RightHand:
    почти финальная Aiming-поза

Fire:
    разрешён
```

Смысл:

> «Я уже практически наведён, но ещё не совместил глаз с прицелом».

Это состояние особенно полезно для AI, который знает, откуда ожидается контакт.

---

### 4. Aiming

Полный ADS.

```text
Weapon:
    глаз → прицел → ствол

AimProgress:
    полный

Spread:
    минимальный

Optic:
    учитывается
```

Это твой основной режим точного огня.

---

### 5. HipFire

Особый CQB-режим.

Здесь я согласен с твоей идеей:

> **HipFire не обязан быть «промежуточным режимом наведения».**

Это полноценный способ стрельбы.

Он особенно подходит:

* неопытным солдатам;
* внезапному контакту на очень короткой дистанции;
* оружию, которое ещё не успели поднять;
* экстремально быстрому огню.

При этом опытный солдат тоже может хорошо стрелять из HipFire — просто за счёт своих навыков.

---

### 6. PointAim

Оружие направлено по ЛЦУ/естественной линии оружия, но **без ADS**.

```text
Optic:
    не участвует

Laser:
    может участвовать в качестве визуального/геометрического ориентира

Fire:
    разрешён

Accuracy:
    хорошая вблизи
    быстро ухудшается с дистанцией
```

И я согласен с твоим новым решением:

> **PointAim доступен даже без ЛЦУ.**

ЛЦУ тогда становится **модификатором PointAim**, а не обязательным условием.

Это лучше для архитектуры.

# Часть 2. Что меняется в архитектуре

Сейчас у тебя `WeaponPoseState` уже фактически содержит `LowReady`, `PointAim`, `HipFire`, `Aiming`, а `NotReady` оставлен вне обычного gameplay cycle. 

Нужно добавить:

```csharp
HighReady
```

Получится:

```csharp
public enum WeaponPoseState
{
    NotReady,
    LowReady,
    HighReady,
    HipFire,
    PointAim,
    Aiming
}
```

Я бы **поставил `HighReady` именно между LowReady и остальными боевыми состояниями**, но физический enum-порядок сам по себе не должен использоваться как логика переходов.

---

# Часть 3. `WeaponPoseMode` и `WeaponPoseState` оставить раздельными

Это важная часть твоей текущей архитектуры и её стоит сохранить. У тебя уже правильно разделено:

```text
WeaponPoseMode
    ↓
EffectivePoseState
```

а `WeaponAimMode` отдельно отвечает за порог выстрела. 

Я бы сделал:

```csharp
public enum WeaponPoseMode
{
    LowReady,
    HighReady,
    HipFire,
    PointAim,
    Aiming,
    Auto
}
```

`NotReady` сюда **не добавлять**.

Почему:

`NotReady` — это не боевой режим, а carry state.

Поэтому:

```text
Ctrl + E
    NotReady → LowReady

E
    LowReady → HighReady → Aiming → HipFire → PointAim → LowReady
```

# Часть 4. Ручное управление

Ты подтвердил:

## `Ctrl + E`

Если юнит находится в:

```text
NotReady
```

то:

```text
Ctrl+E
    ↓
LowReady
```

Это переход:

> «перейти из небоевого состояния в боевое».

---

## `E`

Если юнит уже в боевом режиме:

```text
LowReady
→ HighReady
→ Aiming
→ HipFire
→ PointAim
→ LowReady
```

При отсутствии каких-либо возможностей режима:

```text
PointAim
```

просто пропускается или становится недоступен.

Я бы **не делал E циклическим через NotReady**.

То есть:

```text
E
LowReady → HighReady → Aiming → HipFire → PointAim → LowReady
```

а:

```text
Ctrl+E
NotReady → LowReady
```

# Часть 5. HighReady не нужно сразу делать отдельными ручными координатами

Твоя идея здесь хорошая.

Для первого варианта:

```text
HighReadyWeaponPose =
    Lerp(LowReadyWeaponPose,
         AimingWeaponPose,
         HighReadyBlend)
```

и аналогично для правой руки:

```text
HighReadyRightIK =
    Lerp(LowReadyRightIK,
         AimingRightIK,
         HighReadyBlend)
```

Начальное значение:

```text
HighReadyBlend = 0.70–0.80
```

Я бы начал с:

```text
0.75
```

---

# Часть 6. Но сделать это не просто `Lerp` по всему Transform

Лучше ввести:

```csharp
HighReadyDefinition
```

с:

```text
WeaponBlend
RightHandBlend
```

Например:

```csharp
[Serializable]
public struct HighReadyDefinition
{
    [Range(0f, 1f)]
    public float WeaponBlend;

    [Range(0f, 1f)]
    public float RightHandBlend;
}
```

Почему?

Потому что может оказаться:

```text
WeaponBlend = 0.75
RightHandBlend = 0.62
```

Оружие уже почти в Aiming, а рука чуть дальше от финальной позиции.

Это намного лучше, чем заставлять обе системы иметь один коэффициент.

# Часть 7. Для HighReady сделать optional override

На оружии можно иметь:

```text
HighReady:
    UseDerivedPose = true

    WeaponBlend = 0.75
    RightHandBlend = 0.70

    Optional custom pose
```

По умолчанию:

```text
UseDerivedPose = true
```

Если конкретная винтовка плохо смешивается:

```text
UseDerivedPose = false
```

и настраиваются отдельные:

```text
HighReady Weapon Pose
HighReady RightHand IK
```

Таким образом в 90% случаев у тебя нет дополнительных ручных настроек.

# Часть 8. Что происходит с левой рукой

Левую вообще не добавлять в эту систему.

Она остаётся:

```text

 ↓
ForeGrip

LeftHandGrip
 ↓
LeftHand IK
```

То есть HighReady автоматически получает правильную левую руку потому, что само оружие уже переместилось.

Это именно то, чего мы хотели добиться раньше.

# Часть 14. Но здесь вмешивается ранг

И это хорошо.

В твоей текущей системе ранг уже непосредственно влияет:

* `Marksmanship` → spread;
* `WeaponHandling` → aim time;
* `RecoilControl` → recoil recovery. 

Это **не нужно дублировать в pose system**.

То есть:

```text
FinalAimTime =
BaseWeaponAimTime
× DistanceMultiplier
× PoseMultiplier
× WeaponHandlingMultiplier
× TraitMultiplier
× MovementMultiplier
× StanceMultiplier
```

# Часть 16. HipFire — особый случай

Твоя идея:

Мне она нравится.

Но важно:

**HipFire не должен означать «плохой солдат».**

Он означает:

А ранг определяет, насколько хорошо конкретный солдат умеет им пользоваться.

# Часть 19. Почему нельзя просто сделать «500 м = в 5 раз хуже»

Потому что на 0–20 м различие расстояния для реакции небольшое, а после 50–100 м влияние должно становиться заметнее.

Я бы использовал **кусочно-плавную кривую**.

Например для времени наведения:

| Дистанция | multiplier |
| --------- | ---------: |
| 0–5 m     |       0.90 |
| 10 m      |       0.95 |
| 25 m      |       1.00 |
| 50 m      |       1.05 |
| 100 m     |       1.15 |
| 200 m     |       1.30 |
| 300 m     |       1.45 |
| 500 m     |       1.70 |

Это не «реальные физические числа», а стартовая игровая кривая, которую потом нужно проверять на твоих оружиях.

# Часть 22. Aiming

Для Aiming я бы **почти не добавлял сильный distance penalty**.

На дальности 500 м проблема должна идти больше через:

* weapon dispersion;
* optics;
* marksmanship;
* recoil;
* movement;
* target size;
* incomplete aim.

А не через:

```text
500m → ×3 AimTime
```

То есть:

```text
AimingTime:
25m → 1.0
100m → 1.05
300m → 1.10
500m → 1.15
```

# Часть 27. Но не делать резких переключений

Использовать hysteresis.

Например:

```text
HipFire → PointAim
    > 10m

PointAim → HipFire
    < 7m
```

А:

```text
PointAim → Aiming
    > 35m

Aiming → PointAim
    < 25m
```

Так AI не будет постоянно:

```text
PointAim
Aiming
PointAim
Aiming
```

если цель колеблется возле порога.

# Часть 29. Реакция AI

У тебя уже ранг содержит `ReactionTimeMin/Max`, это отдельная характеристика, которую не надо смешивать с `AimTime`. 

Поэтому:

```text

    ↓
```

Иначе хороший ранг будет ощущаться просто как «быстрее прицеливается», хотя на самом деле он должен ещё и **быстрее реагировать**.

# Часть 32. Ранг не должен напрямую менять fire threshold

Это важное правило.

Ранг уже влияет на:

```text
AimTime
Spread
Reaction
Recoil
```

Я бы **не давал рангу напрямую снижать RequiredAimProgress**.

Почему?

Иначе Elite начнёт стрелять почти мгновенно всегда.

Лучший солдат должен:

* быстрее подготовиться;
* быстрее повернуть оружие;
* стабильнее держать оружие;
* лучше контролировать recoil;
* лучше стрелять в движении.

Но **сама доктрина огня** должна определять, насколько быстро он решается стрелять.

Это сохраняет смысл `WeaponFireDisciplineMode`.

# Часть 76. ЛЦУ — итоговая роль

После изменения:

```text
PointAim
```

не требует ЛЦУ.

ЛЦУ добавляет:

### Basic Laser

```text
PointAim spread ×0.95
PointAim aim time ×0.95
```

с сильным эффектом на:

```text
0–30m
```

---

### Improved Laser

```text
PointAim spread ×0.88
PointAim aim time ×0.90
```

с эффектом примерно до:

```text
50–100m
```

и дальше стремится к нулю.

В Aiming можно дать небольшой acquisition bonus, например:

```text
Basic: ×0.97
Improved: ×0.92
```

но **не давать ЛЦУ прямой бонус к итоговой ballistic precision при полном ADS**, если у тебя оптика/прицел уже отвечает за эту часть.

И обязательно: **занести эти два набора modifiers в attachment-модификаторы ЛЦУ после основной реализации pose system.**
